# MPP Handling of inbound trampoline

Duplicate (?) tracking of trampoline secrets:
- We track our trampoline secret in `HTLCSource`. It's the same for
  all inbound HTLCs, so we don't need it per-hop.
- We also track it in `HTLCPreviousHopData`, this is from trampoline
  receives. We do want our trampoline secret so that we can double
  wrap the error for the recipient.

  hops on hand.
- Yes I think that we could remove it; or we could just continue to
  have the duplication (it's not a train smash, leave on the list).

Claude changes:
- `fail_htlc_backwards_internal`:
  - Use `incoming_trampoline_shared_secret`: yes, we should always
    double wrap errors.
  - Match on the `error_code`:
    - If we could decode it, the error is for us. This means we can
      switch it out for our own temporary error because it isn't
      relevant to the downstream recipient.
    - If we have a peeled error that we couldn't decrypt all the way,
      then it's for the original sender and we just treat it like it
      is a regular failure (say it's from downstream and encrypt it).
    - If neither of these, the error is borked.

- `DecodedOnionFailure`:
  - We need to add `trampoline_peeled_packet`, because it means that
    we're an intermediate node that the error isn't for. We need this
    error to pass it back to the original recipient.
